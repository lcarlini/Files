Tasks for App Manager and Generated Applications
These tasks apply to both the App Manager and the applications generated by App Manager. The generated application is the primary consumer of the security, session, API, auditing, rules, caching, and trigger functionality. The App Manager itself also needs authentication and permission-based access to its dashboard and app models.

Scope and Architecture
The overall system will have several layers:

Generated application UI — the final application created through App Manager, which must include a login screen and client-side security behavior.

App Manager UI — the administrative application used to create, configure, deploy, and manage generated applications.

Security reverse proxy — validates the session and permissions before forwarding requests to APIs.

Caching reverse proxy — handles Redis-backed caching for GET requests.

APIs — execute business logic and are aware of the AMI, data sources, core tables, and detail tables.

Executor / event layer — receives post-save triggers, handles downstream workflows later, and performs cache invalidation.

Azure Storage — stores write audit records and read/write access logs.

Redis — stores compact user role/permission data and cached API responses.

The first version should remain intentionally simple. Avoid solving edge cases, advanced optimization, or full workflow automation now. Get the complete flow working first, then refactor later.

Generated Application: Login
Add a login screen to the final application generated by App Manager.

When a user accesses a deployed generated application, such as the Documents app, the expected behavior is to present a login screen before allowing access to the application.

The generated application should authenticate the user and obtain a user ID.

Intra/SSO can be used to obtain the user ID and is likely the initial login approach.

After successful authentication, create a session ID.

Send the session ID with every subsequent API call made by the generated application.

The generated application should use the security information returned by the system to determine what the user can see and do.

Do not display UI elements, pages, buttons, or data that the user is not authorized to access.

Do not allow the user to submit write operations for objects or actions they do not have permission to perform.

App Manager: Login and Access Control
Add authentication to the App Manager itself.

App Manager currently has no security because that was simpler for the initial version, but it must now have authentication.

A user must be authenticated before accessing App Manager.

Apply permission-based access control to the App Manager dashboard and app model/configuration screens.

For a given application, a user must be a developer or owner to view its dashboard and model.

He indicated that this access would be above level 60.

Users in the 80–100 range should be able to see what is happening in an app and make changes through the App Manager.

Do not spend time finalizing exact permission thresholds now.

Use simple numeric permission levels for this version, such as 0, 25, 50, 75, and 100.

Return a numeric permission value for each object.

A value of 0 means the user cannot see or access the object.

A value of 100 means full access.

Intermediate values represent partial access.

Apply the same security principle in App Manager: hide what the user cannot access and enforce the permission check on the server as well.

Universal User Model
Create a universal user concept for the system.

For now, call these entities users, even though the system may later need master accounts or resources that can log in.

Every user must have a unique user ID.

A user can have any number of unique login identifiers.

Supported login identifiers may include:

Intra/SSO

Email

Phone number

Social-media login

The specific login method does not matter as long as it resolves uniquely to the user.

SSO is acceptable and should create a unique identifier that can be associated back to the user ID.

A user can have multiple passwords or credential types.

Examples include:

Standard passwords

One-time passwords

PINs

Passwords with expiration rules, such as a 90-day expiration

When logging in with a password, retrieve all unexpired passwords associated with the user.

Use one-way encryption/hashing to validate the supplied password against the stored credentials.

After successful authentication, create a session.

Session Management
Create a session ID when the user logs in.

The session ID is the central mechanism used throughout the system.

Store the session ID in the universal authentication system.

Record session metadata, including:

Where the user logged in from

Browser information

IP address

Geolocation, potentially obtained through Cloudflare Workers

Any other available session-related information

Send the session ID with every API call.

Use the session ID to look up the associated user ID.

Use the user ID and session context to determine:

The user’s group

The environment

The application being accessed

The user’s roles and permissions

The session must be usable by both the client and server-side security checks.

Roles and Permissions
When a user logs in, retrieve all of the user’s roles.

Place the user’s roles in a fast, accessible cache such as Redis.

Most roles should also be cached in Redis.

Model permissions as a simple one-to-one relationship between a user and their environment.

Each role has an ID that can be looked up in Redis.

The permission model is natively hierarchical and recursive.

An admin permission at a root object should recursively grant access downward through the hierarchy.

A permission can change at lower levels; for example, a user may have 100 at the root but 0 five levels down.

The exact numeric scale is not important at this stage.

Use fixed reference values:

0 means no access; the object is effectively turned off.

100 means full access.

Values in between represent intermediate permissions.

The system needs permissions for at least:

Read

Write

Execute

Admin

These may be represented using ranges, such as dividing 0–100 into four groups of 25, but the exact grouping can change later.

Return a numeric permission value for each object.

Do not over-engineer the permission-number model now.

Client-Side Security
Send the user’s role/security information and AMI-related security data to the client.

The client should include a small security tool or library that can determine whether the user has access to see or interact with something.

The client must prevent the user from seeing content they are not authorized to see.

The client must prevent the user from writing data they are not authorized to write.

The security payload is expected to be small; he estimated around 400 bytes of data.

The payload should contain the user’s role/permission information for each relevant environment.

Send a package of roles for the relevant environments to the client.

Client-side security is not optional: unauthorized UI elements must be blocked or hidden.

However, client-side security alone is insufficient.

Server-Side Security
Perform the exact same permission validation on the server.

When a session ID arrives with an API request, determine the user’s permissions for the specific app and environment.

Check whether the user has the required permission before executing the operation.

Even though the client will usually have already validated access, the server must still verify it independently.

This protects against users bypassing the client or attempting unauthorized actions directly against APIs.

Server-side security is mandatory, not optional.

Security Reverse Proxy
In version zero, implement a standalone security reverse proxy.

The reverse proxy sits in front of the APIs.

The APIs initially have no internal security logic.

The reverse proxy receives the incoming request and reads the session ID.

Based on the request, it determines:

Which app the user is trying to access

Which environment is involved

Which operation is being requested

What permissions the user has

Check whether the user has the appropriate permission, such as read, write, execute, or admin permission.

If authorized, forward the request to the underlying API.

If not authorized, reject the request before it reaches the API.

The API then processes the request and returns the response.

This approach creates an extra call and is more expensive long-term, but it is simpler and appropriate for the first version.

Later, replace or supplement the reverse proxy with a security DLL that the API calls directly, reducing the flow from two calls to one.

For the first version, build and test the reverse proxy as a standalone component.

Test clear allow/deny scenarios:

User can perform the operation

User cannot perform the operation

User has read but not write permission

User has admin permission

User has no session or an invalid session

Recursive Object Security
Implement recursive security checks for objects.

If a user has recursive admin access, such as 100 from the root object downward, allow access without detailed checks.

If the user has 100 recursively across the hierarchy, they can do anything; simply pass the request through.

If the user does not have full recursive access, compare the incoming data against the security tree.

Package the request data in an envelope that allows the system to identify the object name uniquely across the entire system.

Recursively walk the security tree and match the requested object name.

Determine whether the user has access to that object.

Build a quick recursive dictionary or structure describing what the user can and cannot do.

Keep this structure very small.

The goal is to minimize the amount of data stored in Redis.

He gave an example where a protobuf-like structure in Redis could be as small as two bytes.

Use compression where appropriate.

For example, a root object permission of 0 plus a level of 100 may be enough to represent recursive full access.

Use knowledge of the AMI on the API side to expand the compact security data when more detail is needed.

The same recursive algorithm should be used on both client and server.

The client uses it to decide what to show or hide.

The server uses it to decide whether to allow or reject the operation.

AMI-Aware APIs
Make the APIs aware of the AMI.

The APIs must understand the application model, including:

Core tables

Detail tables

Relationships between tables

Data sources

OData-related data

The system has multiple data stores, so the API must know where each type of data lives.

If a request only needs core data, return the core data and do not unnecessarily query detail tables.

In most cases, approximately 99% of the time, only core data will be needed.

If the request also needs data from detail tables:

First resolve and filter the core table.

Then determine which detail table(s) are relevant.

Retrieve the related detail data.

If a search parameter exists in a detail table, use it to identify the corresponding core object/core ID.

Then return the relevant core data and detail data as needed.

If the request can be satisfied by returning only details, return the details directly.

Implement the logic to identify the correct data source for each requested property or object.

For phase zero, keep this logic simple.

Phase Zero: Detail Data Behavior
For phase zero, if any requested property exists in any detail table, return all properties from that detail table.

Do not attempt to return only the exact requested columns in this phase.

This is intentionally simpler for the initial implementation.

For saves in phase zero, accept all properties sent by the client.

Overwrite the record with the submitted properties.

Do not attempt partial updates or change tracking at this stage.

In a later phase, such as phase 1a, continue returning all data from the API but hide unrequested fields on the client.

In phase 2 or later, implement updates that only modify the columns that actually changed.

Parent-Child Relationships
Track the parent’s eTag so the system knows that the parent exists.

This avoids unnecessary additional lookups when saving child records.

For example, when saving 5,000 invoice line items, do not perform 5,000 separate invoice ID lookups.

Save the invoice IDs directly.

This provides a major performance improvement and is safer.

Treat insert, update, and delete as variations of a unified save operation where practical.

The system cares about the latest timestamp/version of the data rather than treating each operation as a completely separate concept.

Save Auditing in Azure Storage
For every write operation, create audit records in Azure Storage.

Save two files for each written record:

{guid}-current.json

{guid}-{timestamp}.json

The current.json file represents the latest state of the record.

The timestamped file preserves the historical state at the time of the write.

This will cause storage usage to grow significantly over time, and that is acceptable.

The audit record should include the session ID.

Using the session ID, the system should be able to trace back to:

The user

The login information

The IP address

Other session metadata

Who performed the action

This enables investigation of object histories and identification of who changed what.

Do not store the session ID in Cosmos DB.

Keep session-related information in the separate audit/session storage.

The current.json file can contain more information than what is stored in Cosmos.

He acknowledged that Azure Storage write costs are not ideal, approximately $5 per million writes, but considered the audit capability valuable enough to implement now.

Storage cost after that was described as approximately $0.02 per gigabyte per month.

Read and Write Access Logs
Track both reads and writes for almost any object.

Create an additional folder in the same Azure Storage structure for access logs.

For any given object in any given environment, record who read or wrote it.

Record access at least once per session.

Keep the implementation simple at the beginning; more complexity can be added later.

This log helps identify stakeholders before making changes to an object.

For example, if an object was accessed within the last 30 days, the system should know who to contact and say that a change is being made.

This provides traceability for both data access and data modification.

Trigger / Executor Stub
After a save operation completes, send a trigger indicating that certain row IDs changed.

For now, this trigger can go to another component or Azure Function.

The Azure Function can be a stub; it does not need real downstream workflow logic yet.

The trigger/executor logic must live outside the API.

The API should return synchronously and confirm that the data was saved.

All downstream workflow processing happens later, asynchronously.

Do not build the full downstream workflow in phase zero.

Later, the executor will also handle cache busting.

When data changes, the executor should delete or refresh the relevant Redis cache entries.

This makes cache invalidation event-driven.

Rules Engine
Start building a basic rules engine inside the AMI.

Store rules separately from the main AMI definition.

Rule changes must not change the semantic version of the AMI itself.

Rules can change frequently, even 50 times per day.

Use semantic versioning with three levels:

Major

Minor

Rule

The rule level has its own incrementing version number.

Implement simple initial rules using this structure: property operator value or property operator property

Initial supported operators:

Equals

Not equals

Greater than

Less than

Greater than or equal to

Less than or equal to

Determine comparison behavior based on the property data type.

Use built-in C# libraries for comparisons and validation.

Do not write custom comparison logic unnecessarily.

Use capabilities already available in EF where applicable.

Example rule: an invoice’s due date must be after its creation date.

During a save, evaluate the applicable rules.

For phase zero, if any rule is violated:

Reject the entire save.

Return an error explaining why.

Stop at the first rule violation rather than collecting all validation errors.

A successful test case is: if a due date is before a start date, the entire save fails and the API returns the reason.

Later, add an all-or-nothing configuration option that can be turned on or off.

Later, the client will receive DLLs and TypeScript interfaces to perform validation before sending data to the API.

Client-Side Validation
The generated application will have forms on the client side.

Run validations through WebAssembly (Wasm).

For each object, return validation errors as plain text.

When defining rules, capture the human-readable error message.

Eventually, users should be able to define rules in natural language.

Example: “The due date cannot be before the start date.”

AI will later help convert those plain-language rules into rule definitions and C# validation logic.

The system will generate the rule, required rule information, and the error message.

The client should display validation errors visually, such as a red indicator on the invalid field.

Later, bake validation directly into UI controls.

Example: if there are two date pickers, prevent the due date from being selected before the start date.

Do not implement the advanced UI-level validation behavior now.

For now, support basic property/operator/value comparisons.

Later, support dynamic rules such as:

“Due date cannot be after 2030.”

“Due date cannot be more than 90 days in the future.”

Later, support custom C# validation functions that return true/false.

Example: checking whether an investor group has sufficient funds before allowing a stock purchase.

Caching Reverse Proxy
Add a second reverse proxy between the security proxy and the APIs.

This proxy handles caching for GET requests.

If the requested data already exists in Redis, return it directly from Redis.

If it does not exist, call the API, retrieve the result, and write it to Redis.

Use the API URL as the basis for the Redis cache key.

Example cache keys:

GET invoice

GET invoice page 1

GET invoice prod page 1

After a write occurs, the executor/event layer should invalidate or refresh the relevant cache.

Make cache invalidation event-driven.

If a cache entry does not exist for some reason, the system should handle that gracefully.

The executor should delete the relevant Redis key when data changes.

Do not build the full caching and cache-busting implementation immediately; this comes after the initial security and API work.
